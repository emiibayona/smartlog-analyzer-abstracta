## Integration with Google Gemini
Analyze batches of logs for patterns and repetitive issues using Gemini's
GenerateContent API with JSON Schema output. Chunk large batches, validate and
synthesize findings, then persist the report. The engine handles provider errors,
safety blocks, wrong output formats, and timeouts without persisting partial success.

## DB
- Every log will have this schema:
    - `microservice` - from which microservice
    - `date`
    - `level` - Level error from microservice
    - `payload` - File resource
    - `message`
    - `id`
    
- Every analysis will have this schema:
    - `microservice` - from which microservice
    - `date`
    - `result` - Text or log generated by AI after process the logs.
    - `message` - A summary with the result.
    - `id`
    - `status` - [Pending, In progress, Completed, Failed]
    - Engine metadata: microservices, logIds, inputReferences, logCount, chunkCount, model, promptVersion, levelCounts, completedAt, errorCode.
    - `report` - Validated structured summary, patterns, commonIssues, insights, each finding referencing input evidence IDs. `result` retains its JSON-string representation.

# Api endpoints

## GET
- [GET] `/api/logs` - Retrieve list of logs, with filters [date, microservice, level, message], pagination.
  - Filters combine with AND: exact microservice and level, UTC day (`YYYY-MM-DD`), and case-insensitive literal message substring.
  - Pagination: `page=1`, `limit=20` by default, maximum limit 100; sort by date descending then ID descending.
  - Response: `{ data, pagination: { page, limit, total, totalPages } }`. Invalid queries return JSON HTTP 400.
- [GET] `/api/analysis/` - Retrieve List of analysis, with filters [date, microservice, message, status], pagination.
  - Same pagination and UTC day/literal message behavior as logs; status exactly `Pending`, `In progress`, `Completed`, or `Failed`.
  - Response `{ data, pagination: { page, limit, total, totalPages } }`; unknown/repeated/invalid parameters return 400.
- [GET] `/api/analysis/:id` - Retrieve the analysis by {id}
  - Returns a single record with string `id`; malformed ObjectId returns 400, missing record returns 404. Query parameters are not supported.
- [GET] `/api/health` - Health check
  - Live MongoDB ping with a bounded deadline; returns 200 when ready and 503 otherwise.

## Runtime safeguards
- Validate environment configuration before connecting or listening.
- Apply client/server query deadlines and indexes for common log filters and newest-first sorting.
- Generate request IDs and structured operational logs without raw credentials, headers, or log payloads.
- Run integration/E2E tests against a separate test API and ephemeral MongoDB instance on an isolated Docker network.

## Analysis engine — internal service, no new endpoints in this wave
- Use Google's Gemini GenerateContent API with a key in the x-goog-api-key header, configurable compatible model, response JSON Schema, local validation, and no enabled tools or automatic retries.
- Validate a bounded batch, redact common secrets, and analyze whole-record chunks. Correlate multi-chunk reports in a final synthesis pass; reject invalid/unknown evidence references.
- Limit logs, serialized input, chunk count, response bytes, output tokens, request time, and total provider time. Do not silently truncate input or persist partial success.
- Persist Pending/In progress/Completed/Failed transitions. Save validated reports, evidence references, deterministic counts, and model metadata. Store only safe failure codes on provider errors or timeouts.
- Mixed-service analyses use microservice `multiple` plus a microservices array. Non-stored input references are positional; no raw batch or file payload content is sent/stored as metadata.
- Configuration is optional for normal API startup, required when analyzing: GEMINI_API_KEY, GEMINI_MODEL, ANALYSIS_MODE (default synthesis), ANALYSIS_REQUEST_TIMEOUT_MS, ANALYSIS_TOTAL_TIMEOUT_MS, ANALYSIS_CHUNK_BYTES.
- Persist provider `gemini` on newly generated reports; preserve historical records without relabeling their provider.
- ANALYSIS_MODE is the configurable LLM focus, sent in every request and persisted as metadata. Internal chunk/synthesis phases remain separate from this focus.
- Test integration with a local HTTP provider stub and isolated MongoDB: valid output, wrong formats, refusals, provider errors, and timeouts. No paid calls in automated tests.
- Process-crash recovery, durable job queues/retries, and analysis-triggering endpoints are deferred.

## POST
- [POST] `/api/logs` - Receive a log to insert
  - UTF-8 JSON object, 64 KiB maximum; strict required field/type/date/service/level/length validation and no unknown fields.
  - Confirmed valid insert returns 201. Readable invalid submissions and unconfirmed primary writes go to `rejected_logs`; confirmed fallback returns 202 with reason/issues and request ID.
  - Malformed/empty body: 400; oversized body: 413; unsupported type/encoding: 415. Transport failures are not quarantined.
  - Neither write confirmed: 503 for sender retry. Same-database fallback does not survive complete MongoDB outages; timeouts/retries can duplicate writes.
- [POST] `/api/logs/analyze` - Receive a group of logs to analyze.
- [POST] `/api/logs/stored/analyze` - Receive a group of IDs of stored logs to analyze.
